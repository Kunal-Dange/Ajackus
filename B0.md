# B0 — The `count` trap

What does `terraform plan` show when a middle landlord account is removed from the list? Why is
that dangerous here? What's the fix?

<!-- Your answer here -->
Terraform addresses resources created with count by numeric position.

[ la-001, la-002, la-003, la-004 ]
If lets say landlord-2 as "la-002" is removed, the desired state list becomes [ la-001, la-003, la-004 ].

Terraform still compares the resources by index as :
Index 0 = la-001
Index 1 = la-003
Index 2 = la-004

Index 1 changes its desired bucket identity from la-002 to la-003, so it changes replacement in the terraform state file. Similarly for the other buckets.

The plan will contains a replacement cascade and a destroy for resources whose logical landlord accounts still exists.

Why is that dangerous here? -> This is dangerous because s3 replacement or deletion can disrupt the access and depending on content, high risk of data loss.

What's the Fix? - > The fix is to use the "for_each" instead with stable landlord Account IDs as keys:

variable "landlord_accounts" {
    type = set(string)
}

resource "aws_s3_bucket" "landlord_media" {
    for_each = var.landlord_accounts
    bucket = "haven-media-${each.key}"
    tags = landlord_account_id.each.key
}

With for_each addresses are keyed by Account ID such as aws_s3_bucket.landlord_media["la-003]. Removing the  'la-002' then affects only that account's bucket. The addresses of other buckets will remain same..
